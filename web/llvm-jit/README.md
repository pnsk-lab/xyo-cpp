# xyo-cpp Browser LLVM JIT (experimental)

This directory contains a **unified xyo-cpp runtime** built with Emscripten `-sMAIN_MODULE=2`, a browser LLVM llc/wasm-ld Worker pipeline, and a restricted SB3 compiler that emits LLVM IR calling the same xyo runtime variable helpers as the interpreter. The runtime host and the browser IR compiler API / dynamic-link host were adapted from [pnsk-lab/xyo-editor](https://github.com/pnsk-lab/xyo-editor/tree/main/packages/llvm-wasm) (retain its license and attribution).

## Verified on the current xyo-cpp tree

- Emscripten links the full xyo interpreter runtime, the actual JIT ABI helpers from `src/jit/rt.cpp`, and a dynamic-loading host.
- Node E2E: a genuine zipped SB3 green-flag script executes on the interpreter; a PIC side module generated by **native LLVM llc + wasm-ld** invokes `xyo_var_set` in the **same** xyo runtime. The snapshot observes both writes.
- Node E2E: `emitRuntimeIR` derives IR from a real SB3, compiles it with real native LLVM, loads the side module with `dlopen`, binds its AOT slots, invokes it, and observes variable value `42`.
- Non-admitted scripts run with the xyo interpreter. Failing compilation or binding never intentionally suppresses their execution.
- `bun test`: 21 passing tests, including the native-LLVM/unified-host integration cases.
- `bun run check` and `bun run build`: pass.

**Not verified**: end-to-end LLVM compilation **inside a browser**. The prebuilt wasm32 LLVM llc and LLD tool images are not checked in or available in this checkout.

## Build the integrated xyo runtime

From repository root:

```bash
source ~/.emsdk/emsdk_env.sh
emcmake cmake -S web/llvm-jit/native -B web/llvm-jit/native/build -G Ninja -DCMAKE_BUILD_TYPE=Release
cmake --build web/llvm-jit/native/build --target xyo_browser_unified -j 4
node web/llvm-jit/native/smoke.mjs  # requires previously generated build/side/side.wasm
```

Build the reference side module with native LLVM as a **test-only** tool:

```bash
llc -mtriple=wasm32-unknown-emscripten -relocation-model=pic -filetype=obj \
  web/llvm-jit/native/side-smoke.ll -o web/llvm-jit/native/build/side/side.o
wasm-ld --shared --allow-undefined --export=xyo_browser_script --export=xyo_aot_slot_0 \
  web/llvm-jit/native/build/side/side.o -o web/llvm-jit/native/build/side/side.wasm
node web/llvm-jit/native/smoke.mjs
```

The JS integration test `bun test tests/unified-runtime.test.ts` generates its own side module from SB3 and requires the Emscripten main module built above plus native `llc` and `wasm-ld` on PATH.

## Browser usage

From `web/llvm-jit/`:

```bash
bun install
bun run copy:host
bun run copy:artifacts -- /path/to/checkout-of-xyo-editor
bun run dev
```

`copy:host` copies the two built `xyo_browser_unified` artifacts. `copy:artifacts` requires four separately built browser LLVM tools under xyo-editor's `packages/llvm-wasm/.work`:

- `llvm19-browser-proof/llc-browser.mjs` and `.wasm`
- `llvm19-lld-browser-proof/lld-browser.mjs` and `.wasm`

These are **not** source files and the copy script does not build them. Without the LLVM tool images, the browser UI can still load and interpret SB3 projects using xyo-cpp, but cannot compile a script with LLVM. A separate Worker contains the runtime and is terminated after execution or timeout.

## C++ codegen port

`native/browser_ir_api.cpp` is the real `jitEmitScript` wrapper adapted from xyo-editor. It emits PIC wasm32 LLVM IR with AOT slot metadata when compiled as an Emscripten executable against an LLVM build targeting wasm32. Configure with:

```bash
emcmake cmake -S web/llvm-jit/native -B web/llvm-jit/native/build -DXYO_BROWSER_BUILD_COMPILER=ON \
  -DLLVM_DIR=/path/to/wasm32-llvm/lib/cmake/llvm
cmake --build web/llvm-jit/native/build --target xyo_browser_ir
```

This compiler target **has not yet been built or verified on this checkout** because a WebAssembly-targeted LLVM library build is absent. The existing UI currently uses `src/runtime-ir.ts`, a deliberately restricted TypeScript compiler, rather than `jitEmitScript`. This path does not cover arbitrary Scratch code and its numeric variable value representation is not yet parity-proven for all Scratch conversions.

A native diagnostic build of `browser_ir_api.cpp` succeeded and generated actual xyo C++ LLVM IR from SB3, but that native emitter embeds **64-bit host struct offsets**; its output must **never** be loaded into the wasm32 host. `src/compiler-metadata.ts` rejects mismatched pointer size, offsets, tags and slot metadata when the real wasm32 C++ compiler integration is enabled.

## Limitations

- LLVM path: a single green-flag script with up to eight inline finite numeric-shadow set/change blocks. Unsupported projects run under the interpreter.
- The host interpreter supports many additional Scratch blocks but this minimal browser host does **not** yet expose drawing, audio, keyboard or mouse host callbacks. Those features require the xyo-editor renderer and audio bridges, updated for the current tree.
- No arbitrary LLVM-compiled loops, fibers or scheduler yield points. Compiled straight-line scripts are invoked at the green flag boundary; the interpreter owns all other scheduling.
- The imported wasm side modules share the runtime's linear memory and are **not a security sandbox**. Never load unverified third-party wasm modules or assume that checking metadata protects against malicious code.
- The source files in `native/` are compiled against the **current xyo-cpp tree**, not the older source commit pinned by xyo-editor.
