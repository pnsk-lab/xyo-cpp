# ScratchBench: 30億整数乱数のパリティ失敗 (2026-11-04)

## 再現条件・切り分け

ScratchBenchパリティの `Operators: Pick Random Rules 2` Test 5で、`random(0, 3000000000 * 1)` を30回実行し、`round(r) == r && r >= 0 && r <= 3000000000` を確認する。通常約2123/2123だが、GUIの`play`による実行では少数回だけ2122/2123となっていた。

- 元のSB3を変更せず`play`で繰り返したところ36回目に同じ失敗を再現した。
- 乱数処理を取り出した`run`ではインタプリタ・Eager・HotSpot各200回とも成功。ループを20万反復に増やした各12回も成功した。これはCPUで実行されるため。
- `XYO_GPU=0`で全体`play`を18回実行し、18回とも2123/2123。
- LLVM IRを調べると、該当するワープ手続き `xyo_script_0_p160` の先頭に `xyo_gpu_repeat` があり、成功時はCPUの`xyo_random`を呼ばずループ全体をGPU実行する。
- GPU経路有効時にはCPU乱数ヘルパに30億上限の呼出しが無かった。一方`XYO_GPU=0`ではCPUで30回呼び出した。

## 根本原因

GPU仮想マシンは数値を32-bit浮動小数点数(f32)で表現する。GLSL `gpu_vm.comp` の `OP_RAND` は端点が両方整数でも符号付き32-bit整数範囲を超えたら「浮動小数点乱数」経路を選んでいた。Scratchはdoubleで`isInt`と判定し、30億でも整数乱数経路を選ぶため意味論が一致しない。f32の低い値域では小数が生じ、その場合`round(r)==r`が偽になる。高い値域ではf32自体の刻み幅が1以上のため、たまたま整数に見え、失敗が断続的になった。

さらに`float(uint32_seed) * (1.0/2^32)`はseedが大きいとf32への丸めで1.0になりうる。GLSL `rnd()`を1未満へクランプし、整数乱数の結果も与えられた範囲内へクランプする。

## 修正

`src/gpu/gpu_compile.cpp`の`operator_random`について、**両端が型を保存できる静的な整数リテラルで、絶対値が8388607以下**の場合のみGPU VMへ下ろす。それ以外（大きい範囲、算術式、変数、非整数）はGPU並列ループをコンパイルせず、既存のCPU JITへフォールバックする。これは単なるベンチマーク用条件ではなく、f32でScratchの整数乱数と両端を正しく表現できるための保守的な数値証明。

`src/gpu/shaders/gpu_vm.comp`で、丸め誤差により乱数が1.0になることと範囲外整数を返すことを防ぐ。小さい整数乱数を用いたGPU描画は引き続き利用できる。浮動小数点乱数や変数による範囲は性能より正当性を優先してCPUに戻す。シード列の厳密一致は要求しない。

`tests/gpu/test_parallel.cpp`には0..10、負数を含む小さい整数、上限8388607のGPU受理、30億の直接/算術式、非整数、変数端点の拒否を追加。

## 注意

この修正の範囲はGPUの乱数命令。CPUの`rt::randomInt`・LLVM JITの基本乱数処理には変更が不要。さらに一般的なGPU数値演算のf32／Scratch double間の差異がないことを証明したわけではない。将来のGPUサブセット拡張では、端点と出力の値域解析を追加し、ダイナミックな数値でも厳密な型ガードを使ってGPU化可能性を広げる。

## 修正後の検証結果

- 追跡コードを撤去した最終ビルド: 成功。
- CTest: 11/11成功（新しいGPU数値範囲のコンパイル判定を含む）。
- 元のパリティSB3（診断用15ブロックを復元時に除去した複製）をGUIの`play`/HotSpotで16回連続実行し、すべて2123/2123。
- 生成LLVM IR上で該当手続き`xyo_script_0_p160`を調査したところ、修正前の`xyo_gpu_repeat`呼び出しは0になり、`xyo_random`呼び出しが残った。
- 診断を残した中間ビルドでは、修正後の元の全体実行が2123/2123で、30億整数乱数のCPU JIT呼び出しが30回であることを確認した。
