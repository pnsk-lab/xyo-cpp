# SB3初期リスト文字列の共有

## 変更内容

[SB3ローダ](<../src/load/sb3.cpp>)で、初期リスト内の同一文字列をロード中に共有するようにした。文字列Valueの型や内容を変えるのではなく、同じ不変SStrを参照する。リストの各Valueスロットは独立したままで、要素の置換・削除が別のスロットの値を書き換えることはない。

共有の対象は初期リスト値だけである。数値・bool、スカラー変数、ブロックのフィールド、動的に作る文字列、SB2のロード経路は変更していない。単一スプライトの読み込みは同じSB3ローダを使うため、そのインポートごとに別の共有範囲を持つ。

キーは完全一致するUTF-8文字列で、大小文字、数値の綴り、色の表記、埋め込みNULも区別する。例えば`"1"`と`"01"`や`"#aabbcc"`と`"#AABBCC"`を同じキーにはしない。空文字列も従来どおりheap上のSStrとして作る。

`XYO_SB3_LIST_INTERN=0`で共有を無効にできる。この設定はロードごとに読む。SStrの文字データは既存設計で不変として扱われ、数値・RGBの遅延キャッシュは既存のatomic出版プロトコルを使う。

## 容量と寿命

キャッシュは1回のロードだけ存在し、以下の上限を持つ。

- 4,096キー。
- 保持するキーのUTF-8長の合計は1 MiBまで。mapノードなどの管理領域は別。
- 1キーの長さは4,096バイトまで。

上限に達した後も既存キーのヒットは利用する。新しいキーを入れられない場合は、従来どおり別のSStrを割り当てる。キャッシュを消去・退避して共有率を保証する方式ではない。

キャッシュはキーを所有するが、SStrポインタはGCから借りるだけで、解放しない。標準コンテナ自体はGCルートではない。既存の`Gc::DeferCollect`が、全ターゲットをRuntimeへ接続するまでのロード区間を保護する。キャッシュをdeferガードより後に宣言し、defer解除より先に破棄する。将来この区間に明示的なcollectを追加する場合は、未登録ターゲットとキャッシュの両方のルートを見直す必要がある。

Scratchの文字列値としての比較・保存内容は維持する。一方、C++から観測する`SStr*`の同一性や生の`Value.bits`は、以前別々だった同じ文字列どうしで一致する場合がある。ロードをまたぐ共有、上限を超えた値、動的文字列を含む全体の正規化は保証しない。

## 実プロジェクトの割り当て確認

3D2をロードし、緑旗を動かす前にリストの文字列Value数とSStrポインタ数を数えた。

| 対象 | 文字列値の数 | 共有なしの実体数 | 共有ありの実体数 |
| --- | ---: | ---: | ---: |
| buffer:color | 172,800 | 172,800 | 53 |
| texture data | 180,000 | 180,000 | 53 |
| 全初期リスト | 353,695 | 353,695 | 542 |

`Gc::bytesAllocated()`のロード前後差は22,190,692→581,554 bytesだった。これはGC管理バイトの増分であり、RSSやプロジェクト全体の消費メモリを表す値ではない。

同じ確認実行のロード時間は200.888→147.202 msだったが、各1回なのでロード速度の結論には使わない。描画速度は、ロード・JIT・ウォームアップを除いた別の交互A/Bで検証する。

## 回帰と描画速度

[専用テスト](<../tests/unit/test_list_string_intern.cpp>)では、共有範囲と容量の境界、元の文字列と型、保存・再ロード、独立したリスト要素とclone、GCを確認する。最後の参照が別ターゲットだけ、またはcloneだけになった状態でもGC後に内容を読み出す。同じ共有文字列のcoldな数値・RGBキャッシュへ4 OSスレッドからアクセスするケースも含む。

全体ビルド成功後、CTestは6/6成功した。固定した実行ファイルでも、JIT・インタプリタ・共有無効の3設定で全unit suiteが成功し、共有文字列は各4,789チェック・失敗0だった。これには元のリストと別ターゲットのリストから参照を順に取り除くGCケースと、同じ文字列の数値・RGBキャッシュを並行初期化するケースを含む。

Scratch executeフィクスチャもJIT・インタプリタ・共有無効JITの各設定で116/116成功した（assertは336／339／336、失敗0）。unit内の条件付きスケジューラdispatch検査2件は実行条件が揃わずskipされた。全unitログとフィクスチャ結果は[固定バイナリの検証記録](<../build/list-intern-final-ab/run_regressions.py>)と同じディレクトリに保存した。

## 最終A/B：CPU描画

[固定バイナリ用スクリプト](<../tests/bench/list_intern_ab.py>)で同じ実行ファイルを使い、共有なし（`XYO_SB3_LIST_INTERN=0`）と共有あり（`1`、既定も有効）を交互に5回ずつ比較した。順序はoff/on、on/offを交互にした。HSV整数化など他の既存最適化は両群で有効で、SB3は変更していない。

CPU計測時はOpenGLレンダラを初期化できなかった。最初のGL向け実行はGPU統計の検査で停止し、結果には採用していない。GPUアクセスの変更後に行ったOpenGL計測は後節に分けて記録する。以下は`SDL_VIDEODRIVER=offscreen`、`SDL_RENDER_DRIVER=software`、`XYO_PEN_CPU=1`を明示した**CPU描画だけの比較**である。過去のOpenGL計測の時間や改善率とは直接比較しない。

ステージ480×360、表示scale=2、Res=1、seed=1。ロード・JIT・開始クリック・60 activeフレームのウォームアップを除外し、sleepなしの90描画フレームを測った。ウォームアップ後に主スレッドだけをCPU 12へ固定し、既存のドライバスレッドや通常再生の設定は変更していない。詳細プロファイルとトレースは無効。

| Res=1・90描画フレーム、各5回の中央値 | 共有なし | 共有あり |
| --- | ---: | ---: |
| 描画込みwall time | 3,286.594 ms | 3,107.914 ms |
| 全プロセスCPU時間 | 3,777.347 ms | 3,586.789 ms |
| 描画込みスループット | 27.384 FPS | 28.958 FPS |
| wall timeの範囲 | 3,272.042〜3,292.090 ms | 3,101.483〜3,149.832 ms |

wall timeは約**5.44%短縮**、スループットは約**5.75%増加**した。CPU時間は約5.04%短く、5組全てで共有ありのwall timeが短かった。この環境・作品・描画条件での実測であり、全作品やGPU描画で同じ改善率を保証するものではない。統計的有意差の主張もしない。

全試行で15,552,000ストローク、draw=90、quads/flush/readback=0、upload=90を照合した。並列スケジューラのdispatchなども両群で0だった。画像確認用のRes=4は各1回で、972,000ストローク、draw/upload=90。時間は1,022.233→959.891 msだったが、この単発値は性能結論に使わない。

画像比較は各解像度の最初の組の最終フレームに対して行った。Res=1は867画素（x=630..719、y=54..69）、Res=4は933画素（x=618..718、y=54..69）が異なり、いずれも実時間依存のFPS数値表示内だけだった。**FPS表示以外はbyte一致**した。全フレーム・全試行の画素一致を検証したという意味ではない。

### 計測の固定と再現

スクリプトは実行ファイルを新規ディレクトリへコピーし、各試行の前後にSHA-256を照合する。プロジェクトのハッシュ、CPU固定、ウォームアップと描画回数、ストロークなどの統計も検査する。継承した`XYO_*`設定は削除し、必要な設定だけを指定する。Pythonのassertを無効化する`-O`や`PYTHONOPTIMIZE`では実行を拒否する。

最終計測の実行ファイルSHA-256は`8a9a3d7915a1eb440495411d8ec50a62414b2c52d21d6d76b82f4640272e6255`。生ログ・画像・ハッシュは[最終計測ディレクトリ](<../build/list-intern-final-cpu-ab/manifest.json>)と[集計](<../build/list-intern-final-cpu-ab/summary.json>)にある。初期の非固定バイナリ計測は途中で再リンクされた可能性があり、最終結論には使っていない。

```sh
cmake --build build -j 2
ctest --test-dir build --output-on-failure
# 出力先には未作成のディレクトリを指定する。計測中にビルドしない。
python3 tests/bench/list_intern_ab.py --backend cpu \
  --cpu 12 --output build/list-intern-recheck
# OpenGLを利用できる環境では --backend gl を指定する。
# バックエンドの統計が期待値と違う場合は、混在させず停止する。
```

以前のロード割り当て確認のソース・ログは`build/list-intern-ab/`にある。ロード中の実体数と、ウォームアップ後の描画速度は別の測定である。

## GPUアクセス変更後のOpenGL計測

GPUアクセスを変更した後、同じ固定バイナリでOpenGL経路を再確認した。診断結果はNVIDIA GeForce RTX 3070、OpenGL 4.3.0、ドライバ615.78.08、共有コンテキスト有効（`shared=1`）だった。レンダラやランタイムのソース変更・再ビルドは行っていない。

`SDL_RENDER_DRIVER=opengl`とNVIDIAのEGL vendorを明示し、共有なし／ありを交互に各5回測った。Res=1、90描画フレーム、60 activeフレームのウォームアップ、seed=1、主スレッドCPU 12固定、計測からロード・JIT・ウォームアップを除く条件はCPU計測と同じである。CPU計測とは別の比較として扱う。

| OpenGL・90描画フレーム、各5回の中央値 | 共有なし | 共有あり |
| --- | ---: | ---: |
| 描画込みwall time | 2,371.931 ms | 2,040.332 ms |
| 全プロセスCPU時間 | 2,361.941 ms | 2,034.878 ms |
| 描画込みスループット | 37.944 FPS | 44.110 FPS |
| wall timeの範囲 | 2,289.972〜2,401.176 ms | 2,015.658〜2,187.215 ms |

wall timeは約13.98%短縮、スループットは約16.25%増加した。5組全てで共有ありの方が速かった。これは今回のGPU・作品・条件での結果であり、他の条件で同じ改善率を保証するものではない。

全Res=1試行で15,552,000ストローク、quads同数、draw=90、flush=180、readback/upload=0を照合した。CPU描画へのフォールバックはなく、並列スケジューラdispatchも両群で0だった。描画確認用のRes=4は各1回で、972,000ストローク、quads同数、draw/flush=90、readback/upload=0。時間は447.921→322.643 msだったが、この単発値は性能結論に使わない。

最初の組の最終画像は、Res=1で1,010画素（x=618..718、y=54..69）、Res=4で842画素（x=619..731、y=54..69）が異なった。いずれもFPS数値表示内で、表示外はbyte一致した。最初の画像検査はRes=4の(731,64)の1画素を領域外として拒否した。全体画像を確認するとFPS数字のアンチエイリアス端であり、RGB差は(255,140,26)→(255,141,29)だった。除外領域の右端だけを730から731へ変更し、保存済み画像を再検査した。計測の再実行や試行の除外は行っていない。
