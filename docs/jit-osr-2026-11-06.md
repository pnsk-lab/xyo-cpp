# xyo-cpp LLVM OSR（On-Stack Replacement、2026-11-06）

## 目的と対応範囲

`XYO_JIT_ASYNC=1 XYO_JIT_OSR=1` を指定すると、JITコンパイル完了前にインタプリタで実行していたスクリプトを、**安全なトップレベルループの繰り返し境界から**LLVM生成コードへ移行できる。

- 既定のOSR適用対象：トップレベルの `control_repeat`（`TIMES` が純粋な数値リテラル）。インタプリタの `ExecContext.loopCounter` を確認し、残り反復数をそのまま受け渡す。
- 実験対象：`control_repeat_until` / `control_while`。条件をループ先頭から再評価するため private induction counter は不要。ただし今回の実測では通常経路より遅いため、追加で `XYO_JIT_OSR_CONDITIONAL=1` を指定した場合だけ移行する。
- OSR不可：動的 `TIMES`、再帰・手続き内にあるループ、スタックが深い場合、warp実行中、レポータの中断状態がある場合、`repeat` カウンタが未初期化・NaN・負値・非整数・2^40超の場合など。この場合はインタプリタを継続し、次の新規呼出しから従来JITを利用する。

非同期JITおよびOSRは現在opt-in。これらの環境変数を設定しない場合、既定のJIT動作は変わらない。Eager JITとAOTも従来通り。

## 移行プロトコル

1. `LLVMBackend::prepareAsync` はランタイムスレッドで通常のJIT関数と、選択したループブロックから始まる別の **OSR継続関数** を生成する。これは元の `greenFlag` ハットからの関数ではなく、ループ本体と **その後続ブロック** のみを含む。
2. 通常関数と継続関数の独立したLLVM IRをワーカーへ渡し、ワーカーがO3最適化・機械語生成を行う。完了結果は通常のCompiledScriptと共にメインスレッドへ公開する。
3. `Runtime::step()` では、コンパイル完了後の各スレッドについて、`stack.size()==1`、現在のブロックがOSR対象ループ、`StackFrame::isLoop`、レポータ・非同期中断が無い、などの条件を検査する。
4. `repeat` の場合は `loopCounter` を `JitCtx.osrRepeatRemaining` に移す。通常JITが元の `TIMES` を再評価すると副作用や反復回数が変わるため、OSR用関数は `TIMES` の代わりにこの値をロードし、元のカウンタが整数であることを検査する。
5. インタプリタの一時フレームを終了して、JIT互換ヘルパが期待するルートフレームを作り直し、`thread.osrActive` をマークする。
6. `Sequencer::jitStepThread` は、通常の `cs->entry` ではなく `cs->osrEntry` をFiberまたは同期経路で呼び出す。ブロック列の前半を再実行することはない。
7. スクリプト末尾まで完了したら従来のFiber終了処理で回収する。異なるブロックグラフへinvalidateした場合は旧世代のコンパイル結果を公開しない。

## 安全条件

- `TIMES` はシャドウの `math_number` / `math_integer` / `math_whole_number` / `math_positive_number` だけを対象とする。動的数値レポータは毎反復で評価される可能性があるためOSRで省略しない。
- トップレベルのループヘッドにいること、ルート以外のインタプリタスタックがないことを保証する。入れ子・手続き中のスタックをJIT先頭へ飛ばすことはしない。
- `StackFrame::executionContext` に保存された有限・非負・整数の残り回数を使う。負の0や浮動小数点の一意性を崩さない。
- `warpMode`、`waitingReporter`、`reported` 等の状態を安全に再構築できない場合は移行しない。
- OSR用JITと通常JITでGCピン留めを共有し、継続関数が参照するGPUプログラムの所有権もCompletedScript側に移す。

## 検証

`tests/differential/jit_osr.py`：実行途中の `repeat`、25万反復の数値更新、前置文の副作用、後続の命令、連続する2ループ、250000.5の端数カウンタ、12万要素のリスト追加、ネストされたループ、動的TIMES、手続き内ループ、`repeat until`、`while`。インタプリタ、非同期JIT、OSRで**変数・リストの最終内容が一致**することを確認する。安全な長大ループではログに `[jit-osr] promoted` があることもチェックする。

実装後の固定バイナリ `build/osr-eval/xyo-osr-final`、SHA256 `929ccd881b0417eb83171e7310c320c66570505bac79a14c68db601ce7ce9d06` で9種類の差分ケースが成功した。ScratchBenchの`loops_repeat`、`loops_foreach`、`vars_setchange`、`algo_sort`、`app_ast`、`app_brainfuck`、`app_life` でもOSR OFF/ONのチェックサムが一致した。

同一バイナリ・CPU12固定、8ペアを乱択順で実行しプロセスのwall time（起動・コンパイル・実行終了まで）を測定した結果：

| ケース | OSR OFF | OSR ON | wall速度比 |
| --- | ---: | ---: | ---: |
| 25万回の単純な `repeat` | 75.14ms | 65.30ms | **1.148倍** |
| 約21万回の `repeat until` | 83.01ms | 89.01ms | 0.933倍 |
| 約21万回の `while` | 82.75ms | 88.76ms | 0.935倍 |

`repeat until` / `while` は遅いので明示的な追加実験フラグのときだけ有効化。測定生データ `build/osr-eval/bench-results.json`（Git管理外）。計測対象は固定形のループで、一般のSB3全体に速度比を外挿しない。

## 使用方法

```bash
# 協調的な非同期JIT + 正式に検証したtop-level repeat OSR
XYO_JIT_ASYNC=1 XYO_JIT_OSR=1 build/xyo run project.sb3 --jit hotspot

# 条件付きループのOSRも試す（実験的。今回の測定では遅くなる）
XYO_JIT_ASYNC=1 XYO_JIT_OSR=1 XYO_JIT_OSR_CONDITIONAL=1 \
    build/xyo run project.sb3 --jit hotspot

# 実際のOSR切り替えログを出力
XYO_JIT_ASYNC=1 XYO_JIT_OSR=1 XYO_JIT_OSR_TIMING=1 \
    build/xyo run project.sb3 --jit hotspot
```

## 未実装

- 実行中の手続き、ネストしたループ、任意の命令ブロックからの汎用OSR
- 有効なレポータやローカル手続き引数など任意のスタック状態の再構築
- OSR後のdeoptimization（ネイティブからインタプリタへの戻り）の一般化

これらには、スクリプト全体で同一のループID/プログラムカウンタと、ライブ値・命令ポインタ・スタックフレームの写像が必要。今回の実装は、そこへ拡張するための、実際に途中移行する最小限の安全な垂直スライスである。
