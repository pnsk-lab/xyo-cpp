# 3D2 本体のホットループ最適化

## 対象と方針

スレッドの並列判定を改善するだけでは、3D2の毎フレーム描画を速くできなかった。主な負荷はdrawターゲットの1本のスクリプト内にあり、共有変数を使うラスタ処理とペン発行が直列に連なっている。

今回はSB3を書き換えず、次の汎用的なJIT／ランタイム処理を改善した。画質、描画点数、三角形の順序、浮動小数の加算順序は変えていない。

## 採用した変更

### 1. 短いASCII文字列との等値比較

3D2は表示ループで色バッファを`"n"`と比較し、ラスタループではテクスチャ値を`"none"`と比較する。元の汎用比較は、数値変換、文字列キャッシュの検査、比較ヘルパなどを通っていた。

JITは入力ASTから、長さ1〜8のASCII英字だけのtext shadowを認識する。ただし元の綴りが数値として解釈できる場合は対象外にする。例えば`"Infinity"`は数値比較の意味を持つので、文字だけを比較してはならない。

- 両入力は最適化判定の前に、従来どおり左から右へ評価する。
- 動的文字列の最初のASCII文字が違えば、後続を数値化せずfalseにできる。
- 同じ長さで全てASCIIなら、大文字小文字を畳んで直接比較する。
- 非ASCII文字や、判断にUnicodeの性質が必要な場合は元のヘルパへ戻す。
- 非ヒープ値の直接false化は、数値・bool・色などの文字列表現が一致し得ない1文字リテラルだけに限定する。複数文字の`"true"`や`"NaN"`には元の比較を使う。

ASTから認識するので、文字列がスロット経由になるAOTにも対応する。3D2に固有のブロックIDや作品名を実行系へ埋め込んだ変更ではない。

### 2. 数値化済みの座標を再変換しない

JITは移動命令の入力を既に数値化し、移動後の座標も計算している。しかし描画接続時はboxed Valueを受けるヘルパへ戻り、同じ変換と座標計算を繰り返していた。

`xyo_mot_setxy_num(JitCtx*, double, double)`を追加し、求めた座標を共通の`Target::setXY`へ直接渡す。ステージ／ドラッグ判定、フェンス、移動フック、描画通知、ターゲット更新は従来と同じ処理を通る。

計算済み座標を再びScratchのtoNumberへ通してはいけない。既存座標と無限大の加算から生じたNaNなどは、そのままsetterへ渡す必要がある。新ヘルパはこの点も保持する。

### 3. 安定したVariable*だけを関数入口で取得する

従来は変数を読むたびに、概ね次のポインタ列をたどっていた。

```text
JitCtx -> varSlotData -> slot[index] -> Variable -> value/list
```

生成コードはスクリプト入口で全スロットを解決する。その後、同じネイティブ関数の実行中にスロット配列の中身やVariable*自体を入れ替える経路はない。手続きは同じスクリプトのスロットを使い、yieldは同じfiberを再開する。再起動は新しいThreadを作る。

そこで手続きのIRインライン化後に、各ネイティブ関数で必要なVariable*を一度ずつロードする。トップ入口では、配列をresizeし得る**最後の**`xyo_varslot_init`より後に置く。

固定するのは最終的なVariable*だけである。

- Variable.valueは引き続き実メモリへ読み書きする。
- Variable.list、SListの長さ、itemsポインタや各要素も固定しない。
- コールバックによる値変更、リストの遅延生成・realloc、GC、再帰、yield後の変更を観測できる。
- 異なるIDが同じ変数へ解決される場合も許す。IDごとのnoaliasは付けない。
- AOTの共有Moduleでも、変換対象とスロット番号は当該スクリプトの関数だけに限定する。

### 4. 無彩色のHSV変換

彩度0かつ正規化済みの色相が有限なら、RGBの3成分は全て同じ明度になる。従来どおり色相の正規化と彩度／明度のクランプを行った後、`floor(v*255)`を一度計算して3成分へ返す。

RGB入力をそのまま使う変更ではなく、必要なRGB→HSV→RGB往復と丸めを保持する。非有限の色相は従来経路へ残す。

3D2のテクスチャの非`"none"`109,177要素は全て十進数の文字列で、うち44,190要素がグレーだった。これは実行中のヒット率ではなく、アーカイブの静的な分類である。

### 5. 不正なリスト添字でLLVM poisonを作らない

リストread/replaceは、doubleから整数へ変換した後に範囲判定していた。NaN・無限大・表現範囲外の`FPToSI`はLLVMではpoisonになる。

数値のfast pathでは、変換前に順序付き比較で`d >= 1 && d < double(len)+1`を検査する。有効側だけで切り捨てと0-based化を行い、無効側は空文字／置換なしとする。正の有効な小数添字の切り捨ては維持する。`last`・`random`などのヘルパ経路と、INDEX→ITEMの評価順も変えない。

## 採用しなかった試行

### 粗いメモリ型メタデータ（TBAA）

変数値、リストポインタ、リストヘッダ、要素、JitCtxを別の保存領域としてLLVMへ伝える試行も行った。しかし3D2の同一バイナリ比較では、メタデータ有効728.467ms／無効724.470ms（各3回の中央値）で、改善を確認できなかった。複雑さだけを残さないため、**この試行は撤去した**。添字の安全なガードは残している。

### RGB/HSVキャッシュの容量拡大

既存2,048エントリを16,384へ増やす案も調べた。3D2の非透明テクスチャは52種類のRGB色しかなく、現行ハッシュでは全52色が別バケットに入る。テクスチャ配列を順に再生するモデルでは、両サイズとも初回52ミス／2回目0ミスだった。実行中の実測ヒット率ではないが、容量不足を示す根拠がないため増やしていない。

### 未採用の並列化

BSPの三角形は同じ画素へ書き、最初のwriterを優先するため、単純には並列化できない。走査線の補間も浮動小数の反復加算であり、`初期値+k*差分`への置換は丸めを変える。

将来、行を並列化するなら、短い逐次前処理で正確な行初期値を求め、共有scratch変数を私有化し、出力範囲の非重複と順序付きペンcommitを証明する必要がある。今回はその証明のない並列化を入れていない。

## 最終計測

Intel Core i7-12700、RTX 3070、SDL offscreen/OpenGL、stage 480×360・表示scale=2、固定seed。開始クリックを同じフレームで注入し、ロード／JIT初期処理／60 active warmup frames（33msペースで約2秒）を除外した。計測中はCLIのsleepを入れず、通常のRuntime.step→描画を30回実行した。

変更前ライブラリへ同じベンチソースをリンクした対照と、最終版を交互に5回ずつ比較する。詳細プロファイル・ログ・トレースは無効。元のSB3は変更していない。

| Res=1・30描画フレーム（交互5回の中央値） | 変更前 | 最終版 |
| --- | ---: | ---: |
| 描画込みwall time | 830.201 ms | 765.518 ms |
| 1フレームあたり | 27.673 ms | 25.517 ms |
| スループット | 36.136 FPS | 39.189 FPS |
| 全プロセスのCPU時間 | 828.203 ms | 763.466 ms |

処理時間は約7.8%短縮、描画込みFPSは約8.4%増加した。wall timeの範囲は変更前813.923〜843.546ms、最終版739.984〜834.901msで、5組中4組で最終版が速かった。1組では逆転しており、常に同じ改善率になるという保証ではない。

Res=1の最終画像は867画素が異なったが、全てFPS表示内（x=631..719、y=54..69）だった。Res=4の比較も、異なる1,076画素は全てFPS表示内（x=618..730、y=54..69）で、**両解像度ともFPS表示以外はbyte一致**した。Res=4の30フレームは参考単発値107.654→69.774msだったが、反復した性能結論には使わず描画互換性の確認とする。

各Res=1試行は、5,184,000点／quads同数／draw=30／GPU flush=60／CPU readback・upload=0を照合する。Res=4では324,000点／draw=30／flush=30で画像も比較する。FPS数値表示だけは実時間に依存するため別扱いにする。

初期の追加変更3回ずつの比較では33.874→36.075FPS、スロットアドレス再利用追加後の別の3回比較では37.279→41.513FPSだった。測定時のシステム負荷が異なるため、これらを足し合わせたり、別の試行のFPSを直接比較したりしない。

試行中の同一バイナリ比較（各3回）では、通常728.467msに対し、スロット再取得へ戻すと756.350ms、汎用文字比較へ戻すと782.053ms、boxed移動へ戻すと742.021msだった。相互作用があるため、各差分は合算しない。

## 互換性検証

- CTest 6/6成功。
- Scratch executeフィクスチャはJIT・インタプリタとも116/116成功（assert JIT 336／interp 339、失敗0）。
- 短いリテラル比較21,472チェック：大文字小文字、Unicode、NaN、Infinity、bool、両入力順序、reporter副作用。
- HSV変換383,712チェック：変更前の式を独立した参照にし、グレー全256値、境界の隣接double、クランプ、ランダムHSVを比較。
- 数値移動11,520チェック：描画接続／非接続、ステージ、ドラッグ、可視状態、±0、NaN、±Inf、文字列、フェンス、コールバック順序。
- スロット再利用238チェック：96個の未実行分岐スロット、ネスト・再帰、yield、コールバックの値変更、GCとリストrealloc、IDの名前fallback、clone、restart、複数スクリプトのAOT。
- 添字443チェック：NaN／Inf／巨大値、正負の小数、特殊文字列、同じ変数／リストへ解決されるID。入力式はScratchと同じ一親のreporter treeで生成する。
- 通常設定、CPU並列設定、最適化を無効にする旧経路でもunit検証を行う。

gprofngによるサンプリングも試したが、実行中に収集タイマーが変更され、採取時間が描画時間と一致しなかった。この不完全なプロファイルの割合は、改善の根拠として使っていない。

## 再現

```sh
cmake --build build -j 4
ctest --test-dir build --output-on-failure

export SDL_VIDEODRIVER=offscreen
export SDL_AUDIODRIVER=dummy
export __EGL_VENDOR_LIBRARY_FILENAMES=/usr/share/glvnd/egl_vendor.d/10_nvidia.json
export XYO_SEED=1
export XYO_BENCH_WARMUP_FRAMES=60
unset XYO_PROF XYO_PENPROF XYO_PENLOG XYO_PENTRACE
unset XYO_JIT_EQ_GENERIC XYO_JIT_MOTION_BOXED XYO_JIT_SLOT_RELOAD
build/tests/xyo-pen-bench --project 3D2.sb3 --frames 30

# 個別の旧経路対照。JIT生成時に読むので既存AOTには適用されない。
XYO_JIT_EQ_GENERIC=1 build/tests/xyo-pen-bench --project 3D2.sb3 --frames 30
XYO_JIT_MOTION_BOXED=1 build/tests/xyo-pen-bench --project 3D2.sb3 --frames 30
XYO_JIT_SLOT_RELOAD=1 build/tests/xyo-pen-bench --project 3D2.sb3 --frames 30

# Resを変えた描画互換性確認。値変更は実行中Runtime内だけ。
XYO_SET=Res=4 XYO_BENCH_ACTIVE_STROKES=10000 \
  build/tests/xyo-pen-bench --project 3D2.sb3 --frames 30 --shot res4.ppm
```

既定の再生FPS設定や画質を変更したわけではない。ここで示すのは、同じ描画量を実行するエンジンの処理時間と描画込みのスループットである。
