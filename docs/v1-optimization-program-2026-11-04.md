# v1.0.0 最適化プログラム（初回実装・2026-11-04）

## 現時点の実装

### 1. GC の連続空き領域確保（採用）

`src/core/gc.cpp` と `src/core/gc.hpp`。

- 新規スラブでは `[nextFreeCell, freeRunEnd)` の連続した未使用セルから順に確保。セルごとの `countr_zero(~allocated[word])` を不要にする。
- GC が回収した穴あきスラブでは、残存ビットマップから次の連続空き領域を見つけてから同様に処理。
- スレッド専有のスラブ、`poolGen_` によるGC後のキャッシュ無効化、厳密な `allocated[]` ビットマップの更新は従来通り。
- 一度使ったスラブの不足分は `acquireSlabLocked` 経由で再取得。GCのマーク・スイープはいつでもビットマップを参照可能。
- **既定ON**。互換性診断用の旧経路: `XYO_GC_RUN_ALLOC=0`。

### 2. cons 文字列の内部参照の追跡（採用）

`Gc::drainPending()` 内の連結ノードの `left/right` は、ランタイム自身が生成した正規の `SStr*` 参照である。保守的にスタックの任意のビット列を調べる場合と異なる。

- 内部ノードの子が当該GCに属する小オブジェクトスラブの場合、正規位置を持つGCヘッダの `mark` を直接検査。
- malloc確保、別のcollector由来のポインタなどでは従来どおり `markPtr` / `validHeader` にフォールバック。
- 通常の保守的スタック走査では**いっさい検証を省略しない**。
- **既定ON**。互換性診断用の旧経路: `XYO_GC_FAST_CONS_MARK=0`。

### 3. 回帰テスト・実験基盤（採用）

- `tests/unit/test_gc_pool.cpp` に、3種類のセル寸法を織り交ぜ、複数GC後の穴あきスラブ再利用とrootの生存・内容を検証する回帰テストを追加。
- `tests/bench/algos/bench_gc_allocator_ab.py` に、元のScratchBench原文を変更せず、同じReleaseバイナリで `baseline/run/mark/combined` をランダム順に実行するベンチを追加。各ケースでチェックサムを比較し、不一致なら終了。CPU固定、複数ブロック・生JSONを保存。
- 試作中のバイナリとログは `build/v1-gc-*.log`、結果は `build/v1-gc-*-paired.json` に保存。

## v1.0.0 に向けた残りの主要最適化

### 優先度 A：数値SSA・値域証明

TurboWarpに対して `math_arith` は約0.58倍。現状の定数除数や可変除数の剰余では、`f64` の整数性判定と `i32/i64` への変換がホットループに残る。

- ループ誘導変数の下限・上限・増分を**型と値域付きのSSA**として扱う。
- 別スクリプトの変更、yield、関数呼出し、clone、monitor更新などで証明が失効する場合は通常のScratch演算に戻す。
- 整数に限定できる範囲では同じループの算術・比較・剰余を整数値として保ち、数値変換・boxingをループ脱出時にまとめる。
- NaN・Infinity・負のゼロ・2^53境界・任意の文字列代入・再帰と再入を差分テストする。
- ベンチ専用の定数を見て最適化するのではなく、一般的な値域伝播規則で行う。

### 優先度 A：JIT生成・コンパイル費用

- 既存の遅延コンパイルの実験を、Eager/HotSpot/AOTの互換性のある選択機構に収束させる。
- 関数ごとの呼出し回数とコードサイズを使い、O1/O2/O3の実行性能と初回コンパイル費用の折衷を測定する。
- 手続きの遅延解決、再帰・同時worker実行・fiber再開時の再入をCIで保証する。

### 優先度 A：文字列確保・GC設計

TurboWarpに対して `str_join` は約0.35倍で、今回の4〜5%改善のみでは差は埋まらない。

- consノードのオブジェクトサイズ、ルートの追跡、スラブの回収比率、mallocバックエンドの割合を実測。
- 必要なら世代別nurseryと、GC整合性が証明できる一時ノードの逃避解析を検討する。
- 同じベンチ以外にも長い文字列連結・数値→文字列・短い連結・先頭末尾観測を含める。

### 優先度 B：リスト追加とアプリケーション処理

- `list_append` は約0.72倍、一方 `list_read` は約1.49倍。
- 頻繁なappendで、cap/len/limit検査・外部へのエスケープ・buffer再確保・monitorDirty のコストを分離する。
- `app_ast` は約0.63倍。文字列処理か動的参照かをまずプロファイルし、原因を確認してから手を入れる。

## リリース品質の条件

- TurboWarp、Scratch純正、xyo Interpreter/JIT Eager/HotSpot/AOTでの意味論一致を優先する。
- ScratchBenchの特定の作品・命令パターンに限定した最適化をしない。
- 改善は毎回同じReleaseバイナリのON/OFFで検証し、測定順をランダム化。実行時間・コンパイル時間・メモリを別々に計測。
- 既定の動作が崩れる最適化は無効化できる構成にする。
- v1.0.0のタグ・公開はCIと追加の実プロジェクト検証が揃うまで行わない。
