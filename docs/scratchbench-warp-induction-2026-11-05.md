# ScratchBench ループ性能差: 安全なwarp反復の集約

## 調査

ScratchBench `loops_until` / `loops_while` は `k_i` を1ずつ増やし、定数上限に到達するまで実行する典型的な数値帰納ループ。旧xyo-cppのJITでは、各反復でScratch比較の型ガード・数値変換フォールバック・64反復ごとのwarp時間監視を実行していた。条件側は固定上限でも汎用的な`operator_lt`に戻り、JIT上のホットループが多数の分岐を持つ。

## 修正

`src/jit/codegen.cpp` の `warpInductionPlan`/`emitWarpInduction` が、次の条件を満たすループにだけ新しい経路を生成する。

- `control_while` / `control_repeat_until` の条件は、単純な `変数 < 境界` / `変数 > 境界` と、左右反転した比較。`not` を含む `<=` / `>=` 相当も対応。比較値が更新変数でないことを静的に確認する。
- 境界は静的な数値定数（±2^48の厳密な整数）か、**ループ本体が書き込まない別変数**。別変数の値は各バッチの先頭で再読込する。境界が小数・非数値に変わった場合は従来経路に戻す。
- ループ本体は最大8個の異なる変数について、それぞれ `change x by N` / `set x to x + N` / `set x to x - N` に限る。`N` は絶対値65,536以下の整数定数。変数が重複したり別IDで同名になったりする場合は不採用にする。
- 条件に使う帰納変数の増分が、比較方向に対して**単調に進む非ゼロ整数**であることを証明する。条件に影響する副作用・未知のreporter・プロシージャ呼出し・リスト操作・ペン描画・分岐は不採用。
- 帰納変数だけでなく本体で更新する**全変数**について、実行時にScratchの数値比較が成立し、値が±2^48以内の厳密な整数であることをチェックしてから集約する。数値文字列には対応し、非数値文字列や端数のある値は従来経路へ移る。計算後に±2^48を一時的に超えても、64回分の最大増分は小さいため2^53未満の厳密な整数である。
- warp中のみ適用。非warpでは毎反復yieldする従来処理に戻す。**次の64反復の期限確認箇所** でバッチを必ず区切り、同じタイミングで`emitLoopYield()`を実行する。Scratchスレッドはyield間に割り込まれないため、この限定した算術本体なら中間状態は他スクリプトに見えない。yield後は全変数と境界を再読込する。

`XYO_JIT_WARP_INDUCTION=0` で集約経路を無効化できる（比較計測と診断用）。定数やScratchBenchの名前・プロジェクトIDによる特別扱いは行っていない。

## 結果

同一バイナリ・同一マシンで`XYO_JIT_WARP_INDUCTION=0/1`を交互測定し、各ケース4回の中央値（ops/ms、高いほど高速）。

| ScratchBench | 無効 | 有効 | 倍率 | チェックサム |
|---|---:|---:|---:|---:|
| `loops_until` | 1,365,935 | 11,504,858 | **8.42×** | 20000 |
| `loops_while` | 1,374,636 | 11,534,091 | **8.39×** | 20000 |
| `loops_repeat` | 2,205,679 | 2,213,897 | 1.00× | 20000 |
| `loops_empty` | 3,311,822 | 3,309,504 | 1.00× | 40000 |
| `loops_foreach` | 1,837,417 | 1,833,555 | 1.00× | 200010000 |
| `loops_nested` | 2,150,999 | 2,159,489 | 1.00× | 19600 |
| `loops_ifelse` | 378,795 | 378,498 | 1.00× | 16001 |

元データ: `build/loop-investigation-20261105/expanded-paired.json`（今回の拡張版）。これらの基準プロジェクトでは上限や本体が従来形なので、対象の拡大自体による追加の高速化は表示しない。複雑な分岐やリスト操作・`For each` は引き続き対象外。

### 新しい適用範囲の単独測定

新しく生成した `build/loop-investigation-20261105/affine-multi-timed.sb3` は、動的上限 `limit=50001`、`i = i + 3`、`acc1 += 2`、`acc2 = acc2 - 1` をwarpで反復し、約220msの壁時計時間における反復回数を測る。変更前後のバイナリではなく**同一バイナリの最適化ON/OFF**を4回ずつ交互に実行した。

| 指標 | OFF | ON |
|---|---:|---:|
| 反復/ms（4回中央値） | 1,679,124 | 8,340,374 |
| 改善率 | — | **4.97×** |
| 最終値 | `i=50001, acc1=33334, acc2=-16667` | 同一 |

この新しい形式のループで高速経路が使われることを確認しており、従来の `loops_until` 特化ではない。計測元データ `build/loop-investigation-20261105/affine-multi-ab.json`。

## LLVM標準最適化への移行

従来の `emitWarpInduction()` は、ランタイムガード後に直接 `initial + delta * chunk` を算出する経路を生成していた。新経路では、**整数のSSA PHIで表現した単純な帰納ループ**（最大64反復）を生成し、既存のLLVM `O2/O3` 最適化パイプラインに変換を委ねる。

- Scratch側の静的証明は維持：warp限定、数値型・値域・増分・別名関係・副作用のない本体の確認。
- LLVMに渡すのは、十分にガードされた `i64` の帰納変数・カウンタと単一の閉じたループ。反復後のPHIは終了ブロックの先頭に連続配置する。既存の64反復ごとのwarp期限監視は生成IRの外側に残す。
- LLVM標準のO2/O3最適化後のIRを `XYO_JIT_DUMP2=1` で確認。`loops_while` について `xyo.affine` という一時的なループは残らない。
- LLVMのSCEV APIを使って閉形式へ書き換える専用パスも実験したが、**LLVM標準O2/O3と速度が同等**で、独自の変換処理と保守負担を追加する合理性がないため採用しなかった。
- `XYO_JIT_WARP_SCEV=0` は従来の直接計算経路に戻す比較用の切り替え。デフォルトはLLVM SSA経路。インタプリタと非warp実行は従来どおり。

4回ではなく各3回、同一バイナリ・同一マシンで交互に測定した比較の中央値（ops/ms）：

| ベンチ | 従来の直接計算 | 専用SCEVパス（実験のみ） | LLVM標準O3のみ（採用） |
|---|---:|---:|---:|
| `loops_until` | 12,071,010 | 12,122,418 | **12,160,728** |
| `loops_while` | 12,083,379 | 12,099,269 | **12,109,584** |
| `loops_repeat` | 2,336,325 | 2,327,351 | 2,321,061 |
| `app_ast` | 38,495 | 38,404 | 38,557 |

追加検証としてLLVM O2単独でも `loops_while` の最適化後IRに`xyo.affine`ループが残らず、正常なチェックサム `20000` で11,897,981 ops/msを確認した。測定元は `build/llvm-scev-loop/ab.json`、IRは `ir-native.err` / `ir-o2-native.err`。ポインタアドレスなどのランタイム定数は実行ごとに異なるため、IR全体のバイト単位比較は行わない。

AOT側は既存のLLVM O2標準パイプラインをそのまま利用する。`xyo aot ... --obj` で生成した `loops-while.o` を `xyo run ... --aot` で実行し、10,584,775 ops/ms、チェックサム `20000` を確認した（`build/llvm-scev-loop/aot-run.log`）。

## 回帰テスト

`tests/differential/jit_warp_induction.py` は `warp=True/False` の実SB3を生成し、従来の26種の入力条件に加えて24種の組合せを検査。整数増分、左右反転、not、動的/静的上限、複数変数更新、`set i to i +/- N`、非数値と小数、±2^48精度境界、および65,536超の非適用ケースを含む。インタプリタ、eager JIT、HotSpot、集約無効化モードの最終値を照合する。さらにLLVM標準O2/O3経路と従来直接計算経路の値一致も検査する。CIはCTest `xyo-jit-warp-induction` で起動する。

テスト結果：`xyo-tests` 1件（33.06秒）と関連CTest 5件（17.38秒）は全て成功。最初の全体テストビルドはリンクエラーで停止したが、再ビルド後はリンク・実行とも成功した。
