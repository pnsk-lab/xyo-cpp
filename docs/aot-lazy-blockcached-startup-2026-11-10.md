# START-011：AOT v3でBlockCachedを初回使用時に遅延生成する

2026-11-10。AOT v2のロード時、AOTが実際に参照する
3,291個の`BlockCached*`スロットを解決するために
再帰的な`Blocks::getCachedExecute`を実行し、
計33,152個の`BlockCached`を生成していた。
これらをAOT起動時に必ず作る必要はないため、
**ネイティブAOTのスロット表をv3に拡張し、初回使用時に遅延生成**する。

## 形式と互換性

v3は既定OFFの実験機能である。新規AOT生成時に明示的に
`XYO_AOT_LAZY_CACHE_SLOTS=1`を付けるとメタデータ`"v":3`を出力。
v1（個別シンボル）とv2（配列スロット）のロード経路はそのまま残し、
**生成時の既定形式はv2**のまま。

v3の生成コードだけが、BlockCached型スロットを読み出すときに
`xyo_rt_aot_cached`を呼び出す。
スロットの値は`AotLazyCachedSlot*`という記述子を指し、
ターゲットが所有する`Blocks*`、文字列のblockId、
初回解決用mutex、`atomic<BlockCached*>`を保持する。

初回実行時にのみ`getCachedExecute(blockId)`を呼び、
成功したポインターをrelease-storeで公開。
以後はacquire-loadで返し、mutexを取得しない。
`BlockCached`のポインターは従来どおり
`Blocks::resetCache`で退役しても生存し、
ネイティブ手続きフレーム・GCを跨いで安定する。

コード生成側の`decl(\"xyo_rt_*\")`はmainThread属性も付与する。
遅延キャッシュ構築には共有Blocksの内部ハッシュ表変更があるため、
初回解決をワーカースレッドへ無条件に移すことはしない。
この制約により、Parity fixtureのメタデータでは
mainThreadに割り当てられるスクリプト数が
**v2の180/479からv3では305/479へ増加**した。
単一CPUでのParity完走に問題がなくても、
並列ワークロードに性能影響があり得るため、
v3を既定に切り替えない理由のひとつである。

## ロード時の実測構造

`XYO_AOT_LAZY_DIAGNOSTIC=1`でロード後・実行前の状態を表示する。
同じ2656件ScratchBench Parity、同じロード用バイナリで以下を確認。

| 値 | v2 | v3 |
|---|---:|---:|
| AOTスロット総数 | 8,423 | 8,423 |
| BlockCached型スロット | 3,291 | 3,291 |
| ロード完了時のBlockCached生成数 | 33,152 | **0** |
| 遅延解決記述子数 | 0 | 3,291 |
| コンパイル済みスクリプト数 | 479 | 479 |

## 起動時間

AOT生成済みの2つのオブジェクトを**同じネイティブバイナリ**で
ロードし、CPU10固定、SDL offscreen / dummy audioで
最初のScratch標準出力までを計測。
交互A/B順序を反転し、ネイティブAOTの実ロードをログで確認。

| 環境 | v2中央値 | v3中央値 | v3勝数 | ペア速度比幾何平均 |
|---|---:|---:|---:|---:|
| 独立Release、30組 | 263.3ms | **237.8ms** | 28/30 | 1.134倍 |
| 現行共有Release、24組 | 185.9ms | **168.3ms** | 23/24 | 1.111倍 |

ホスト状態が異なる2つの実験間で絶対起動時間を比較しない。
共有Release実験ではv2/v3を同じ共有ビルドから再コンパイルし、
それぞれ12,623,288B・13,038,344Bだった。
v3はコードにヘルパ呼出しが増えるため、
v2より約415KB大きいが起動時間は減少した。

## 完走時の時間・メモリ

共有Releaseのv2/v3ネイティブオブジェクトをCPU10固定で交互実行し、
2656件のテストを最後まで完走させた。各回とも
`2656/2656 PASS`とネイティブAOTの実ロードを確認。

| 指標（各2回の中央値） | v2 | v3 |
|---|---:|---:|
| 全量完走時間 | 18.76秒 | 18.89秒 |
| 最大RSS | 448.7MB | **421.4MB** |

最大RSSの2回分はv2が456.2/441.1MB、
v3が418.8/424.1MB。約27MBの減少だった。
両形式の全量完走時間はほぼ同程度だった。
2回の少数測定のため、有意な性能差を主張しない。

独立Releaseの3回比較でも、v2最大RSS中央値445.8MBに対し
v3は395.6MB、完走時間中央値は双方18.78秒だった。
ホスト負荷・ビルド条件が異なるため、この値を
共有Releaseの数値と合算しない。

原子的高速経路追加前のv3と追加後のv3は
全量2656件を各2回ずつ完走できた。中央値の壁時計時間は
どちらも約17.76秒で、今回の計測では明確な退行なし。
記述子を`std::deque`へ移す案は24組中10組のみ速く、
起動中央値207.5ms→209.8msとなったため不採用。

## 検証

- 旧Scratch Parity 2123/2123件：
  独立Releaseのv3 AOTがPASS。
- ScratchBench Parity 2656/2656件：
  独立Releaseのv3 AOT、現行共有Releaseのv1/v2/v3 AOTが
  **すべてPASS**。ネイティブAOTロードログを確認し、
  JITへの暗黙のフォールバックを拒否した。
- `xyo-aot-lazy-cache-smoke`：AOT v3専用のCTest。
  初回解決前にはキャッシュ未生成、解決後は原子的高速経路を通り、
  4スレッド×10,000回の再参照でポインター一致、
  `Blocks::resetCache`・ソース削除・完全GC後も
  古い`BlockCached*`とMutation/GC管理文字列が有効なことを確認。
  独立・共有ReleaseでPASS。
- CIへ明示的にv3オブジェクトを生成するステップを追加。
  `"v":3`とランタイムヘルパの存在を検証し、
  全2656件のネイティブParityと
  `descriptors > 0, loaded_cached=0`を要求。
  v1/v2の既存検証を維持。
- 別実験：記述子を`std::deque`に格納する案は
  24組のA/Bでv3起動中央値207.5→209.8ms、
  勝数10/24、幾何平均0.976倍で逆効果。採用せず。

## 未解決の安全性制約：ソース編集と遅延スロット

**v3はエディタのソース変更と同時に使う構成にはまだ対応していない。**
v2ではAOTを読み込んだ時点ですべての`BlockCached`を作り、
編集後も旧世代のキャッシュを保持する。一方v3の未解決の
`AotLazyCachedSlot`はブロックIDだけを保持し、
元の`BlockCached`を持たない。ソース削除・差し替えの後に
初めて解決すると、元のブロックが見つからず
`xyo_rt_aot_cached`が`nullptr`を返し得る。
コード生成済み互換命令がそれを使用すると安全な実行継続は
保証できない。通常のParityと解決済みポインターの退役試験は
**このケースの安全性を証明していない**。

専用CTestには、解決前にブロックを削除した場合に
`nullptr`となる負例を追加した。これは安全な復帰機構の
完成ではなく、現状の制限の再現テストである。
今後は編集時に未解決記述子の旧世代値を保全するか、
古いAOT Fiberからインタプリタへの安全な復帰を
行う仕組みが必要。

したがって`XYO_AOT_LAZY_CACHE_SLOTS=1`を使う場合は、
実行中にスクリプトを編集しない**不変のScratchプロジェクト**
に限定すること。v2が既定である理由は並列実行制約だけではない。

## 使用方法

```bash
# 実験用v3のAOTオブジェクトを明示生成
XYO_AOT_LAZY_CACHE_SLOTS=1 ./build/xyo aot project.sb3 \
  --obj project-v3.o

# 実行時にはコンパイル時の環境変数は不要
XYO_AOT_LAZY_DIAGNOSTIC=1 ./build/xyo play project.sb3 \
  --aot project-v3.o

# 従来v2は引き続き既定
./build/xyo aot project.sb3 --obj project-v2.o
```

既存のAOTキャッシュのオブジェクトを使う場合は、
`XYO_AOT_LAZY_CACHE_SLOTS=1`を設定しただけでは
既存v2オブジェクトがv3に変わるわけではない。
必ず**新規オブジェクトを生成し、v3形式であることを確認**する。

他エージェントの作業ツリーの変更は維持した。
今回の差分はJIT/コード生成/AOTローダーの必要箇所と
新ヘッダ・CTest・CIの追加に限定。コミット・pushは行っていない。
GitHub Actionsの実機リモート実行はまだ未確認。
