# START-003：AOT起動時間分析と実験結果（2026-11-09）

AOTを事前生成したScratchBench Parity（2656件）の起動処理を段階計測し、
複数の低リスク最適化を比較した。**十分な改善を確認できず、
この回の最適化候補はすべて既定化を見送った。**

## 起動内訳

独立したReleaseビルドに測定フックを一時追加した。
共有コードには測定フックを追加していない。
計測対象は実際にAOTロードが成功したGUI
（SDL offscreen、ダミー音声）。

| 起動段階 | 代表的な時間 |
| --- | ---: |
| ZIPの展開 | 3ms |
| JSON解析 | 40〜50ms |
| ターゲット・ブロック構築 | 90〜120ms |
| AOTオブジェクトをORCへ登録・マテリアライズ | 25〜35ms |
| AOTメタデータとスロット処理 | 50〜70ms |

SB3読み込みに約130〜170msかかる点が、さらなる短縮の主因。
AOTには8,423スロット、479スクリプトが含まれる。

## 試験1：LLVM ORCシンボルの一括解決

元のAOTローダーはスロットごとに`lookupSymbol`を呼ぶ。
共通JITバックエンドAPIにまとめて解決する経路を追加し、
LLVM21 `ExecutionSession::lookup` で8,423スロットを一括解決した。

最初の独立ビルドでの8組A/Bでは、スロット処理の中央値が
54.0→47.5ms、最初の出力が300.7→293.4msと短くなった。
しかし現行共有コードからビルドして計り直すと結果が変わった。

| 計測条件 | 逐次解決 | 一括解決 |
| --- | ---: | ---: |
| 共有ビルド・交互8組、起動中央値 | 285.5ms | 295.9ms |
| CPU10固定・交互12組、起動中央値 | 269.0ms | 279.3ms |

CPU固定12組で一括解決が勝ったのは**4組**。
ペア速度比の幾何平均は**0.9761**（一括解決が約2.4%遅い）。
初期の改善は安定して再現しなかったため、
共有コードの追加API・呼び出し・CIの新しいA/B検査を撤回した。

一括・逐次ともに現行共有ビルドでAOTを生成し、
Scratch期待値 **2656/2656 PASS** を確認している。
意味論の退行ではなく、純粋に性能上の不採用。

## 試験2：JSONのエスケープなし文字列高速経路

`memchr`で引用符とバックスラッシュを検索する経路を
検証用スナップショットに追加。
CPU固定前の比較でJSON単体の中央値は44.5→42.0ms。
しかし起動全体で明確な改善がなく、**共有ソースへは追加していない**。

## 試験3：Scratchブロック用ハッシュ表の容量事前確保

`allBlocks` と `order`、`Blocks::allBlocks()` の容量を
読み込み前に予約する方式を検証用スナップショットで試した。
CPU10固定・交互12組の結果：

| 指標（中央値） | 従来 | 事前確保 |
| --- | ---: | ---: |
| ターゲット構築 | 81.0ms | 79.4ms |
| 最初の出力まで | 283.6ms | 280.5ms |

12組中7組で改善。ただし差は約3msにとどまり、統計的・実用的に
採用する根拠が不足するため**共有ソースへは追加していない**。

## 継続する場合の優先順位

1. SB3ターゲット・ブロック構築の処理内訳をさらに測る
2. ブロック構築の中間コピーや多数の小さな確保を削減する
3. 事前コンパイル済みAOTの安全な再利用方式を維持したまま、
   再起動時のプロジェクト構築を削減する設計を検討する

現在の実用的な高速起動経路は既存の
`tools/xyo-aot-cache.ts`（明示的な`prepare`の後に`play`）であり、
これによる前回の起動約334msは維持している。

今回の実験コードは共有コードから差分単位で取り下げ、
他エージェントが同時に作業中の未コミット変更は保持した。
新しい測定結果のみ文書化。commit / push はしていない。
