# 並列スケジューラの判定と固定費の改善

## 実装

### 描画接続を理由に全スレッドを禁止しない

以前は `Runtime::renderer != nullptr` で並列スケジューラ全体を止めていた。現在はスクリプトの効果を次の二つに分ける。

- `AccessSet::safe()`: メモリ依存が解決でき、スケジューラ構造を変更しない。
- `AccessSet::workerSafe()`: 上記に加え、呼び出し元スレッドで実行すべき副作用を含まない。

移動・見た目・ドラッグなどのターゲット更新は、描画だけでなく共通の `refreshTargets` フラグや任意のフックも触るため、ヘッドレス時も呼び出し元で実行する。キー入力と音量測定も、内部の使用キー集合・音量キャッシュを更新するので単なる読み取りには分類しない。

描画・ペン・broadcast・clone・stop・wait・monitor・不明な拡張などの逐次スクリプトの直前には、先行する計算バッチを必ずjoinする。描画をメインスレッドで実行しながら別の計算を重ねる変更ではない。OpenGL/Vulkanの共有バックエンドを呼ぶコンパイル済みスクリプトもワーカーへ渡さない。

コンパイラが互換実行／インタプリタreporterへフォールバックする場合も、生成時に `CompiledScript::mainThread` を立てる。opcode名だけから「純粋」と推測しない。AOTにもこの制約を保存し、メタデータのない古いAOTは逐次実行する。

### 再帰手続きを解析できるようにする

自己再帰・相互再帰のたびに `unknown` として並列から除外する代わりに、到達可能な各手続き本体を一度ずつ走査し、読み書きと副作用の和集合を取る。同じターゲット／Blocks内では手続き本体の静的効果は呼出し回数に依存しない。各呼出しのreporter引数と、再帰呼出しの後にあるブロックも走査する。

### 通常実行では衝突グラフ全体を作らない

以前は各バッチについて全ペアを比較し、対称adjacency、辺の配列、UTF-8変換や`sprintf`を含む衝突理由文字列を作った後、union-findで連結成分を求めていた。DOT出力が無効でもこの費用を払っていた。

新しい `buildDepGroups()` は以下の二走査で同じグループを直接求める。

1. 各メモリキーの最初のwriterを索引し、同じキーのwriterをunionする。
2. 各readerを、そのキーにwriterが存在するときだけunionする。

読み取り同士は結ばない。グループ内のスクリプト順とグループの先頭順は以前と完全に一致する。計算量は全アクセス数をAとして、ハッシュの期待計算量で `O(A α(n))`、追加領域はwriterキー数とスレッド数に比例する。密な共有変数衝突でも全ての辺を列挙しない。`XYO_DEPGRAPH`を明示したときだけ従来の詳細グラフを作る。

これは既存の連結成分モデルを高速化したものであり、依存DAGに基づく新しい実行順序へ変更したわけではない。衝突するスクリプトのspawn順を維持する。

### バッチ実行の固定費

- 適格性判定で取得した依存集合をflushまで保持し、同じキャッシュを二度検索しない。
- バッチ配列の容量を周回間で再利用する。
- 完了済みJitCtxの空きプールをネイティブスレッド別に分け、各スクリプト開始・終了時の共有mutex競合を除く。移動するfiberの実行中コンテキストは所有したまま、完了したワーカー側へ返す。
- 単一タスクはWorkerPoolの共有Batchを作らず同期実行する。少数タスクでは必要な数のワーカーだけ起床させる。
- GC遅延はRAIIで囲み、外側の遅延状態を復元する。全ワーカー完了前にはGCしない。

### 並列化の前提となる競合対策

独立した変数でも、その値が同じSStrを参照することがある。数値／RGB変換の遅延キャッシュは、C++側を`atomic_ref`、LLVM側もatomic loadへ揃えた。payloadとstateの両方がatomicであり、単にstateだけをatomicにしたものではない。文字列は不変なので、複数のpublisherも同じ値を計算する。SStrのレイアウトは変えていない。

リストreporterも、既存Variableのlistがnullなら内部でストレージを作る。その場合は読み取り同士の並列化を許さない。初期化済みリストの読み取りは並列化できる。

プロファイラの関数別共有mapも同期した。このロックは `XYO_PROF` が有効なときだけ使う。

## 性能計測

CPUはIntel Core i7-12700。RelWithDebInfo/O2、LLVM JIT。別プロセス負荷があるため、変更前後を交互に計測した。

### 描画接続あり・8本の独立した計算

同じベンチソースを保存済みの変更前ライブラリと新ライブラリにリンクした。各スプライトは自分の変数に対し、warp手続きで `v = v * 1.000000001 + 1` を2,000,000回実行する。8本とも結果をホストで計算した値と厳密比較する。

- 描画APIは接続するが、実際の画素描画を行わないmock。ゲームのFPSベンチではない。
- `XYO_GPU=0` でCPUスケジューラだけを比較する。
- 初回コンパイルを含む3回をウォームアップとして除外し、9回の中央値を取る。
- プロセスを交互に5回ずつ実行し、その5つの中央値をさらに集約する。

| 指標 | 変更前 | 変更後 |
| --- | ---: | ---: |
| 同一計算量の時間 | 91.019 ms | 15.180 ms |
| 各試行の中央値の範囲 | 90.591–92.398 ms | 13.255–22.655 ms |

約6.0倍。変更後は各プロセスで12バッチ／12dispatch／96スレッド／96グループ（ウォームアップ3回＋計測9回）を確認した。これは描画接続を理由に逐次化されていた独立計算が実際に並列化された効果であり、3D2のFPSが6倍になったという意味ではない。

### 依存判定のみ

新旧の判定処理を同一バイナリで比較。2回のウォームアップ後、21回の中央値。各スクリプトが一つのキーを読む／書く負荷である。

| 512スクリプト | 従来の全グラフ＋グループ化 | 直接グループ化 |
| --- | ---: | ---: |
| 独立した書き込みキー | 0.675193 ms | 0.017302 ms |
| 同じキーの読み取りのみ | 0.186740 ms | 0.013249 ms |
| 同じキーへの書き込み | 8.709475 ms | 0.003122 ms |

最後のケースは全員逐次にする判定である。新実装は密な衝突の全辺・説明文字列を作らないので大きく短縮するが、スクリプト実行そのものを数千倍にしたわけではない。小さい8本の独立ケースでは0.000317→0.000226msで、削れる絶対時間は小さい。

### 変更していない3D2本体

起動・10 active warmupを除外し、同じ30描画フレームを変更前後で交互に3回ずつ測った。全6回で5,184,000点、draw=30、flush=60、readback/upload=0が一致した。

| 3D2の30描画フレーム | 変更前 | 変更後 |
| --- | ---: | ---: |
| wall中央値 | 861.609 ms | 878.397 ms |
| FPS | 34.819 | 34.153 |

この負荷では改善していない。中央値は約2%遅く、各試行は変更前823.949–887.258ms、変更後830.226–896.959msだった。変更後の計測区間の並列バッチ／dispatchは全回0。重い描画が一つのスクリプトに含まれるため、今回の判定強化だけでは分割できない。描画接続ありの独立計算ベンチの約6倍を、この作品の改善率として流用しない。

最初のA/B画像はFPS数値内の593画素だけが異なり、差分boundsはx=648..718、y=54..69。FPS表示以外はbyte一致した。

同一バイナリで `XYO_PAR=0` の独立計算対照は86.738ms（1実行9回の中央値）でdispatch=0。従来から並列化していたヘッドレス負荷の単発比較は12.363→14.235ms、最小値は11.956→12.143msであり、この経路の速度向上は主張しない。負荷・コア配置の変動があり、描画接続の並列化拡大とは別に評価する。

## 検証

- CTest 6/6成功。
- Scratch executeフィクスチャはJIT・interpreterとも116/116成功（assert JIT 336、interpreter 339、失敗0）。
- `XYO_PAR=0` の逐次対照でもunit/deps/string/schedulerテストは成功。GPU無効化を指定しない通常設定でも、同じ計算ベンチで6dispatch／48スレッド（3 warmup＋3 measured）を確認した。
- 依存解析429チェック失敗0。自己／相互再帰と副作用伝播、ランダム400バッチのグループ順まで含む旧実装との完全比較、4096本の読み取り／共有書き込みを含む。
- CPU並列実行を明示したスケジューラ検証86チェック失敗0。描画接続時の実dispatch、共有変数のspawn順、呼び出し元スレッドでの描画・ペン・say、繰り返しyield、低GC閾値でのリスト／文字列保持、互換reporterの除外。
- `XYO_PROF=1`でも同じCPU並列テストを成功。
- ThreadSanitizerで共有文字列変換の8スレッド×12 cold rounds、およびWorkerPoolの20,000可変サイズバッチを成功。これはC++の独立検証であり、JIT生成命令全体をTSanが計装したという意味ではない。

```sh
cmake --build build -j 4

# 変更後の計算並列化と同一バイナリの逐次対照

```

## 制約

3D2の主な毎フレーム処理は一つの描画スクリプト内にある。スレッド単位の判定を強化しても、それを自動で複数の独立スレッドには分割しない。頂点変換・走査線などを並列化するなら、共有scratch変数の私有化、書き込むリスト範囲の分離、ペンの順序付きcommitを別途証明する必要がある。

依存解析のターゲット／モデル編集時のキャッシュ失効は従来のライフサイクルに従う。今回、新たな永続スケジューリング計画キャッシュは導入していない。乱数は従来どおりスレッドローカルであり、逐次実行と同じseed列の再現が必要なら `XYO_PAR=0` を使う。
