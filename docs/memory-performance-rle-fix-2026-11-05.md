# performance.sb3 のTransient Stringメモリ増大修正 (2026-11-05)

## 原因

HotSpot JITの `xyo_transient_append_repeat_packed` は、短い定数文字列の64反復バッチをその場でUTF-16配列に展開していた。文字列を大量生成するワープループでは `AppendLog::append()` の512Bチャンク確保が急増した。Linuxのmalloc呼び出し元追跡で `src/core/string_util.cpp` の確保を確認。

## 修正

`src/core/string_util.cpp` のAppendLogを、通常の256コード単位の生チャンクと短い定数パターンの圧縮セグメントを同一の順序付きコンテナで管理するよう変更。 `appendPackedRepeat` はパターン長と繰り返し数を保持し、隣接する同じパターンのセグメントを結合する。これによりバッチ処理のループ回数・チェックポイントを変更せず、巨大な文字列の実メモリを削減する。

文字列の `unitAt` はセグメント終端の二分探索で文字単位を返し、 `copy` は必要になった区間のみ展開する。以前のスナップショットは論理長で固定され、後続の追加は旧プレフィックスの文字を変更しない。 `appendLogExternalBytes` は圧縮セグメントの実際の保持バッファに基づいて計算する。

## 実測

対象: `debug/projects/performance.sb3` (4 targets, 2310 blocks)。いずれも `--frames 1000000`。

| 条件 | 結果 | ピークRSS | 経過時間 |
|---|---|---:|---:|
| 修正前 HotSpot auto | RSS 1GiB超で停止 | 1049036 KiB以上 | 14.9秒時点 |
| 修正前 Transient無効 | 正常終了 | 248552 KiB | 33.81秒 |
| **修正後 HotSpot auto** | **正常終了** | **253304 KiB** | **34.29秒** |

修正前はOOM回避のため早期に停止しており、修正前の実行時間の比較はできない。実行時間は処理環境や時間依存のベンチの揺れを含むため、速度向上は主張しない。

## 検証

`tests/unit/test_sstr_cons.cpp` に約52万UTF-16コード単位の反復・文字アクセス・古いスナップショット・展開結果の一致・圧縮後の外部領域サイズを確認する回帰テストを追加。

通常のSB3に影響する出力のパリティや長時間実行の比較は、時間依存のベンチだけでは網羅できないため、ユニットテストと既存のパリティ検証も必要。

## 制約

- 定数長1〜4 UTF-16コード単位の packed repeat を圧縮対象とする。長い定数や動的値の repeated append は未圧縮のまま。
- `SStr::view()` が必要になった際には、従来どおり必要な文字列全体を具象化するため、その時点で論理文字列の長さに比例したメモリが必要になる。
- 大きな圧縮文字列の文字走査はセグメント検索とパターン抽出を伴う。変動する大量のパターンではセグメント数と検索時間が増える可能性がある。
