# GC 補助テーブルの保持メモリ削減

## 変更

`PtrSet` は sweep 後に内容を消して再構築していたが、配列容量は最大到達値のままだった。malloc 管理オブジェクトを大量に生成し、その後ほとんどが死ぬケースでは、本体を回収しても GC 自身の検索テーブルが残る。

- sweep 中に malloc 管理の生存オブジェクト数を数える。
- オブジェクト集合とページ集合の再構築時、必要容量が旧容量の 1/4 以下なら配列を縮小する。小さな増減では容量を保持して再確保の頻発を避ける。
- ページ集合を直接構築し、オブジェクトごとにページ番号を保存していた一時 vector を除去する。
- マーク対象、オブジェクト配置、Value/JIT ABI、GC 閾値は変更しない。プール内の文字列は従来どおり slab bitmap で管理する。

## 独立マイクロ測定

Linux/x86_64、`c++ -std=c++20 -O2 -Isrc`。同じ実装の `PtrSet` に 2,000,000 個の異なる整数キーを追加し、従来の `clear()` と新しい `resetForRebuild(100)` をそれぞれ別プロセスで実行。その後 100 個のキーを挿入し、プロセスを待機させて `/proc/<pid>/status` の VmRSS と VmHWM を取得した。各方式 2 回。

| 方式 | 回収後の容量（要素） | 回収後 VmRSS | VmHWM |
|---|---:|---:|---:|
| 従来 clear、1 回目 | 4,194,304 | 36,952 KiB | 52,960 KiB |
| 新 reset、1 回目 | 1,024 | 4,176 KiB | 52,940 KiB |
| 従来 clear、2 回目 | 4,194,304 | 36,960 KiB | 52,928 KiB |
| 新 reset、2 回目 | 1,024 | 4,176 KiB | 53,004 KiB |

**この合成ケースでは、負荷が落ちた後の常駐量が約 32 MiB 減った。過去のピーク RSS を下げる変更ではない。** 実プロジェクト全体の削減量は未測定で、この数値をそのまま SB3 の効果とはみなさない。継続的に多数の生存オブジェクトを持つケースや、slab 内の小文字列が主体のケースでは、この縮小自体の効果は限定的。一時ページ vector の除去は別途再構築時の一時メモリを削減する。

## 回帰テスト

`tests/unit/test_gc_pool.cpp` に、100,000 キー追加後の容量回収、再挿入後の全キー検索、古いキーの消去、小さい容量変動での容量保持、空集合への再構築を追加。

検証結果:

- `cmake --build build --target xyo xyo-tests -j 4` および `--target xyo-cli -j 4` が成功。
- `ctest --test-dir build --output-on-failure -R '^xyo-tests$'` が成功（37.97 秒）。
- CLI の lazy integration / induction ranges / foreach i32 / repeat i32 / transient strings の 5 スイートがすべて成功（計 9.80 秒）。
- `git diff --check` が成功。

描画・GPU・UI スイートや ASan は今回実行していない。
